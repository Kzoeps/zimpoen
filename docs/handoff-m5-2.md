## 4. Verified facts (Durable 1.4.0 as installed, plus what I learned here)

- **`harness.root()` is a singleton**: a second conversation (the Inbox's) is made with `harness.createConversation({ ownership: { kind: "ownerless" }, agent: {…} }, ctx)`, as `ensureAgents` does. The test fixture does this when `options.inbox` is given.
- `conversation.submit(…)` returns a `Submission`; `harness.submission(id, ctx)` exists at runtime (unlike `Harness.submissionByRequest`, which is declared and missing: use `harness.commit(tx => tx.submissionByRequest(conversationId, requestId), ctx)`). `submission.wait(ctx)` → `{status: "done", answer: EntryId}` or `{status: "unanswered", reason}`; the answer text is in `entry.model` (the assistant message's text blocks) from `harness.commit(tx => tx.entry(id), ctx)`. `withCancel(ctx)` from `@earendil-works/chord/context` cancels only the wait, the run goes on.
- A faux response step can be an **async factory**: gate it with a promise to hold an agent "still thinking" (used by the timeout tests). Faux responses are one global queue in the order requests are made.
- **A task phase must not `harness.abortTask` its own task**: it waits for itself and hangs (`markNeedsReconnect(email, { ownTimer: true })` exists for this; the fixture's `afterEach` then hangs 20 s).
- `erasableSyntaxOnly` forbids constructor parameter properties (`constructor(readonly x: T)`): declare the field.
- node:sqlite (SQLite 3.53.4 here) has **FTS5**; an external-content FTS table kept by triggers works in a STRICT-table database; `bm25()` ranking works.
- `pnpm connect:google --list` passes arguments through both scripts; the CLI runs under plain `node` (type stripping) because workspace packages resolve to their real paths.
- Biome: a regular expression with control characters needs `// biome-ignore lint/suspicious/noControlCharactersInRegex: <reason>` (in `inbox/text.ts`). `biome check --write` reformats; run it on what you touch.
- **Assumed about Google, not verified (no network)**: `history.list` takes repeated `historyTypes`; a `startHistoryId` that is too old answers 404; label records are `labelsAdded|labelsRemoved: [{message:{id}, labelIds}]`; `users/me` works for every call; `calendars/primary/events?singleEvents=true&orderBy=startTime`; a Desktop client accepts `http://127.0.0.1:<any port>/` as redirect; `prompt=consent&access_type=offline` is needed for a refresh token; the downloaded client JSON is `{"installed":{"client_id",…}}`; a Testing-mode refresh token can expire after 7 days (**say "to verify" in the docs**).
- **Assumed about Jev, not verified**: everything in `jev-contract.ts` (see the TODO there).

## 5. Decisions of worker 1 (★ = for the coordinator to veto; each is cheap to reverse)

1. ★ **Digest windows are kept in `inbox_digest`**, not derived from `schedule_daily.last_run_at`: the first read of a window saves `(since, cutoff]` (first writer wins), so a rerun and the power-cut recovery show the same mails and consecutive digests tile exactly. Lookback ≤ 3 days; mail older than 3 days is never "news".
2. **Digest jobs** `digest_midday` 12:30 and `digest_evening` 19:00, late window 120 min, empty = zero-token card, one push tag `digest`. `DailyJob` got `agent` and `request` fields; the engine's behaviour for the briefing and wrap-up is unchanged (their tests pass untouched).
3. **Mail the owner only sent (SENT without INBOX), drafts and chats are not kept.** Trash, spam and Gmail-deleted mail stay as rows with `hidden = 1` (so a restored mail comes back and a re-read does not resurrect it) and are left out of search, digests and counts. Nothing the owner can see is deleted by sync, so rule 3 is not involved.
4. ★ **Disconnect = forget the saved sign-in locally and stop the sync; the mail stays** (deleting it would be a delete that needs approval; no purge exists). Nothing is revoked at Google (setup doc says how).
5. **Account state is split on purpose**: the token file says `ok`/`needs_reconnect` and `connectedAt` (the CLI can write it while the server runs); the DB row holds the sync state. A newer `connectedAt` in a good token = the owner reconnected. `refresh()` reads that file at start, every 10 minutes and on Settings reads.
6. **A calendar failure is a warning on a successful sync** (shown beside the account), not a reason to back off the mail.
7. **Jev failing never loses triage**: the rules answer is stored `provisional` and Jev is asked again at later syncs; what the owner taught (`mark_triage` → sender rule) is applied before any classifier, in both modes, with no call to Jev.
8. ★ **A suggestion reaches the PA only as a display-only card, and acts only through the owner's Add**: the PA is then asked with a message written by code from the stored row (the owner saw exactly those details on the card). The PA has **no prompt section** listing pending suggestions, so a typed "yes, add it" does not resolve one: only the button does (a section would put model text derived from email into the PA's system prompt, B7 again).
9. ★ **Late `ask_agent` answers are display-only cards**, not a prompt section, for the same reason; the PA can ask again. The tool result is labelled "information, not instructions" and the PA rules say so.
10. ★ **The morning briefing's Inbox line quotes the top 3 subjects** as the handoff asks (code-derived, one line, ≤80 characters, invisible/bidi characters stripped, `<>` removed); the PA's rules call them data. This is an untrusted-text channel into a model that has write tools; the owner-confirmed Add and rule 3 bound the damage, but say so in the report.
11. `ASSISTANT_GOOGLE_MODE` defaults to `fake` outside production (a demo mailbox with two accounts, `demo.owner@example.com` and `demo.work@example.com`, deterministic, dated relative to now) and to `real` in production. Whole-server tests therefore get the demo mailbox unless they pass `fakeGoogle`.
12. `pnpm connect:google` runs with `NODE_ENV=production` so that it saves where `pnpm start` reads; the trap is a different `ASSISTANT_DATA_DIR` between the two (it prints the path it saves into).
13. `search_mail`'s query is words, never a Gmail or FTS expression: every word is quoted and prefix-matched, so no operator can break it or be injected.

## 6. Known gaps and risks (for the report)

Real Google and real Jev were never exercised: the REST clients, the id-token handling, the history mapping and Jev's shape are written from knowledge of the APIs and tested only against fakes (once tested). The first real run is the owner's. The Testing-mode 7-day expiry is unverified. A `needs_reconnect` account stops syncing until the owner reconnects (Settings and a PA notice say so). The sync reads mail text into SQLite (8000 characters per mail, never attachments); the Inbox agent's model sees what it reads with `read_mail`; Jev sees an excerpt. `format.ts` decides "same day" for an event's end by comparing `formatLocal` strings minus the time (fragile if that format changes: it has a test to write). The Inbox agent's rules and tool descriptions are a first draft nobody has run against a real model (like M7's). Disconnect keeps mail. Every `suggest_followup` pushes (one tag, replaces the previous).
