## 3. Verified API facts (Durable 1.4.0 as installed; the checkout in `~/Projects/personal/pi` differs in places)

- `ToolExecutionApi`: `callId`, `conversationId`, `taskId`, `now()` (Harness clock), `memo`, `commit(tx)`, `createTask`,

- A tool may create a reminder with `conversation.commit((tx) => tx.createTask(Task, input, { ownership: { kind: "conversation" }, background: true }))`.
  `background: true` keeps it out of conversation aborts (the user's Stop) and out of "busy".
- `TaskRuntime`: `sleepUntil(until, checkpoint, ctx)`; `commit(() => ({ status: "running", checkpoint }), ctx)` moves to the next
  phase; `commit(() => ({ status: "terminal", outcome: { status: "completed", result } }), ctx)` ends; `memo(name, ctx)` /
  `memo(name, candidate, ctx)` first writer wins; `report(error)` reaches `onReport` as `task_error`; `conversationId`, `now()`.
- Sleepers wake when `harness.resume()` runs with the injected `now` past `until`. After `Harness.open`, `resume()` is required
  (the fixtures and server call it). Tests: `clock.now += ms; harness.resume()`.
- `harness.inspect(ctx)` → live tasks with `record.kind/input/abortRequested/state` (used by `reconcile` and the parked list);

## 4. Decisions to put in the report (and for the coordinator to veto)

1. **Reminder consistency.** `tasks_item` is the truth, the Durable `app.reminder` task is a timer carrying `{ itemId, gen, at }`.
   It fires only while the row is open, unfired and still has that `remind_gen` and `remind_at`. Every reschedule / complete /
   delete only changes the row (and aborts the old task as housekeeping). A generation is taken in app.sqlite right before the
   Durable task is created, so a rerun after a crash makes a newer one and the orphan is stale. `reconcile()` at start
   re-creates a lost timer and re-links an unlinked one. This closes the M1 note "revisit in M2" **by self-healing, not by
   `synchronous=FULL`** (no reliance on adapter internals).
2. **Firing.** `fire` posts through `deps.post` (a `write` submission, `requestId = reminder:<item>:<gen>`) plus a `posted` memo,
   marks the row, checkpoints to `notify`; `notify` pushes (at least once; one tag so the phone replaces a duplicate) and
   completes. A push failure is reported (`runtime.report`) and never faults the task. The handoff said "memo-guarded
   `submit(write)`": built exactly so, with the requestId as the stronger guard.
3. **Model-visible cards (please confirm).** Reminder and outcome-notice entries also carry `model: [user message]`
   (`PostedEntry.modelText`) so "snooze it" / "did that go through?" resolve. Cost ≈ 40 context tokens per card, no model call.
   To make them UI-only, drop `modelText` in `reminder.ts` and `approvals/service.ts` (`noticeFor`).
4. **Time in prompts.** No clock in any section (cache-friendly: the `tasks` section renders identical bytes however much time
   passes; tested). The model gets "now" from the new **`current_time`** tool, and `add_task`/`update_task` accept
   `remind_in_minutes` so relative asks need no clock. No timestamp prefix on user messages: it would change every message and
   M1's dev echo for every agent.
5. **Destructive tools.** `delete_task` is model-visible and guarded by the `beforeTool` hook (needs an approved, unexecuted
   request for exactly that conversation, tool and target); `propose_delete_task` is the model's way in. On approval the **server**
   runs the action at once (`ApprovalAction.run`, idempotent) and writes the outcome notice; `delete_task` itself only passes the
   hook in the narrow window between approval and execution (a crash), and `recover()` handles that at start. A failed run is
   status `failed` (no automatic retry; the owner asks again). Rejected alternative: hide `delete_task` from the model: then the
   hook would guard a tool nobody can call.
6. **YES.** Exactly the word (trimmed, any case) and only when an unexpired request waits in that conversation; otherwise it goes to
   the model. It never produces a user bubble: the outcome notice says "You replied YES. …". A resent `requestId` returns the same
   notice (`decided_request_id`), never approves a second request. `POST …/messages` still returns `{ submissionId }` (the notice's).
7. **Approval card state is derived** from later `app.notice` entries (entries are immutable); with none, past `expiresAt` the UI
   shows "expired". The server is authoritative: late answers get 409 `conflict`.
8. **Push setup details.** `DELETE /api/push/subscribe` carries a JSON body (every write must be JSON). Subscriptions are validated
   the way a sender needs (https URL, 65-byte `p256dh`, 16-byte `auth`). `ASSISTANT_PUSH_MODE` defaults to `fake` outside
   production. Subject default `mailto:assistant@localhost`.
9. **Dev model `/tool` commands** (`dev-model.ts`): `/tool <name> {json}` makes the scripted model call that tool, then it
   summarises the result. Dev/faux only. Call ids are a hash of the message and the user-turn count, so a regenerated answer after a
   crash reuses the id (rule 8).
10. **Tests changed on purpose** (they encoded the old shape, not a behavior worth keeping): one `migrate` test used two migrations
    with the same sequence number in one module and out-of-order declaration (forbidden by the new policy); `api.test` health is now
    `{ parkedTasks, parked }`; `config.test` path table gained `vapid` and `pushOutbox`.
11. **Other small ones:** PA instructions are code-owned and changed (it now has tools; other agents keep "no tools yet"); due dates
    without a time are stored as end of day with `due_all_day`; ids are `t_` + 8 hex; migrations `tasks/001_items`,
    `tasks/002_call_ledger`, `approvals/001_pending_actions`, `core/002_push_subscriptions`; new deps `web-push@3.6.7`,
    `@types/web-push@3.6.4` (apps/server) and `packages/extensions` now depends on db, shared, chord, pi-ai.
