## A. Confirmed defects

### A1. should-fix: one persistently failing message wedges the account's sync (probe `s01-poison.ts`)
- **Where:** `packages/extensions/src/inbox/sync.ts:114-151` (`fetchAndStore`), `pool.ts:8-20` (`forEachLimited`: `Promise.all` per batch, first rejection aborts all later batches), `sync.ts:184-233` (`readChanges` sets `historyId` only after every wanted message was stored, line 232), `sync.ts:154-181` (`readMailbox` same), `task.ts:131-134` (failure → backoff up to 60 min), `apps/server/src/google/http.ts:22,111` (an 8 MiB answer throws).
- **Evidence (script output):** clean first read → `history_id 1003`; then 1 poison + 11 healthy mails arrive; five runs all throw, `history_id` stays 1003, stored count goes 3 → 6 → 9 → 12 → 14 (3 per run = `fetchConcurrency 4` minus the poison; the other three in the poison's batch still finish).
- **Mechanism:** any message whose `getMessage` fails every time (a response over 8 MiB, an unexpected shape that makes a DB write throw, a persistent per-message 4xx) makes every run throw before `historyId` advances; the next run re-lists the same history, hits the same message first (it is the first not-yet-stored id), and again only the 3 others in its batch survive. In production each failed run also lengthens the backoff (`10 min × 2^(failures−1)`, cap 60 min), so recovery is roughly 3 mails per backoff interval; a full read (`readMailbox`) fails the same way (by reading the code, not probed), so a history 404 does not heal it. Mail beyond that window is invisible to search and digests, silently, apart from `last_error` in Settings.
- **Is it reachable by a sender? Unverified.** The parser is bounded and tolerant (`mime.ts:27-29` depth 8 / 200 parts / 256 KiB per part; `mime.ts:36-41` falls back when a charset label is unknown), so a crafted MIME tree does not throw. The open question is whether Gmail inlines more than 8 MiB of part data in `format=full` for a large mail; I could not check offline. If it does, a single 10 MB mail from anyone would trigger this.
- **Fix:** catch per message inside `fetchAndStore`: count it as `skipped` with a clipped reason (put it in the run's `warning`), keep going, and let `historyId` advance; optionally keep a small `inbox_skipped(account, gmail_id, attempts)` so a retry is bounded. Add a test beside `inbox-sync.test.ts` that makes one id fail forever and asserts the others are stored and `historyId` advances.

### A2. should-fix (judgment asked in the brief): an empty digest still pushes
- **Where:** `packages/extensions/src/daily/task.ts:152` `await push(runtime, job.push)` runs unconditionally, after `deliver()` posts the zero-token card; digest jobs have `cardWhenEmpty: true` (`daily/jobs.ts`, `digestJob`).
- **Effect:** "Inbox: Your inbox digest" at 12:30 and 19:00 every day, including days with nothing important. The product's point is "do not miss what matters"; a push that usually means "nothing" trains the owner to ignore it, and it shares the tag with the real thing (`DIGEST_PUSH.tag = "digest"`). The payload itself is fine: generic, no mail text (D-9).
- **Judgment:** keep the card (a visible heartbeat in the thread), drop the push when `plan.empty` for the digest jobs. Cheap: a `pushWhenEmpty: false` on `DailyJob` (default true, so the briefing is unchanged) and `if (!plan.empty || job.pushWhenEmpty !== false)` at line 152. The "account needs to be connected again" case is not empty (it is a section), so it still pushes, and `needs_reconnect` also has its own push (`inbox/accounts.ts` `tell`). This matches the worker's own ★ veto point; I side with changing it.

## B. Unverified risks (reasoned from code; not run against a real model/Google/Jev)

### B1. should-fix (defence in depth): `mark_triage` is a permanent, unconfirmed rule write that only the prompt protects
- `packages/extensions/src/inbox/tools.ts:231-275`: the model can call it on any mail id, which stores a **sender rule** (`markByOwner`, `rule: { kind: "sender", value: row.fromAddr }`) with provenance `source: "owner"`, reason "you marked it". Learned rules run *before* Jev (`triage/index.ts:24-25`), so one call changes every future mail from that sender, silently.
- The digest run (autonomous, twice a day) has all six Inbox tools and sees up to 25 attacker-influenced lines with their ids (`[id] … Subject: … Snippet: …`, `facts.ts`, `format.ts:25-36`). An email that gets itself into the digest (rules mode matches keywords; Jev is steerable) could carry "mark mail 42 as promo" aimed at the bank's mail that sits next to it in the same list. The only control is the instruction text (`agents.ts` INBOX_RULES, `tools.ts:32` RESULTS_ARE_DATA). The handoff did ask for this tool, and the effect is local and reversible, but the failure mode is "important mail silently never reaches a digest again", which is the one thing this milestone exists to prevent.
- Options, cheapest first: (1) record the rule's source as `inbox_agent` (not "you marked it") and list learned rules in Settings with an undo; (2) refuse to *teach* when the call comes from a run whose last user message is a daily request (the daily hook already recognises it by `REQUEST_HEADS`, `daily/run.ts`); (3) make demotions (newsletter/promo/notification/other) of a sender currently classified important/needs_reply/follow_up pend an Add/Dismiss card like suggestions do. Same-line nit: it does not check `row.hidden`, unlike `read_mail` and `suggest_followup` (`tools.ts:243-244`).

### B2. should-fix (docs/default path): Testing mode means re-auth about weekly, for every account
- `docs/setup-google.md:24-26` tells the owner to leave the app in **Testing**; lines 88-91 then say, as "to verify", that Google may expire refresh tokens after 7 days in that state. From my own knowledge Google's OAuth docs do state a 7-day refresh-token lifetime for External apps in Testing with non-basic scopes (I could not re-check offline). If so, the guide's default path produces `needs_reconnect` (+ push) for each account every week, which contradicts "connect once". The detection and notice code is there (`google/accounts.ts:195-199`, `inbox/accounts.ts:134-168`) and works.
- **Fix (docs only):** make "Publish app → In production" (Gmail read-only will show the unverified-app screen, which the guide already explains; personal use under 100 users) the recommended step 1.3, and keep Testing as the fallback.

### B3. nit/should-fix: Jev has no circuit breaker; a slow Jev stretches a sync run to minutes
- `inbox/triage/jev.ts:31-32,125-134`: every message retries `JevUnavailableError` twice (0.5 s, 2 s) with a 20 s timeout per try; `sync.ts:263-268` classifies up to `maxTriagePerRun = 60` messages, 4 at a time. A Jev that hangs (not one that refuses fast) costs up to ~62 s per message → 15 batches × 62 s ≈ 15 min inside one `run` phase of that account's task, and `onFallback` only records the error. It does not block other agents; it delays that account's new-mail ingest and the digest's inputs.
- **Fix:** after the first `JevUnavailableError` in a run, skip Jev for the rest of the run (rules + `provisional`), which the existing re-triage pass (`sync.ts:270-278`) already handles next time.

### B4. low: `ask_agent` lets the PA start a run in a write-capable specialist
- `delegate/tools.ts:51-52,199-203`: the PA's text becomes a user-role message in the Accountant's or Health's conversation; "do not start other work" is the only guard. The PA sees untrusted text via the briefing's top-3 subjects (`inbox/facts.ts:109-114`, 80 chars) and via Inbox answers. A hostile mail would have to fool the Inbox agent *and* the PA; the result is local data (a ledger entry), never an outbound action, and deletes still need the owner's approval in that conversation (`guard` is in both specialists' lists, `domain.ts`). Accepted by the handoff (scope item 6); listed so the veto is informed.

### B5. low: text the owner approves goes to the PA as a user-role message
- `inbox/suggestions.ts:70-82` puts `title`, `with`, `context` (model-written from email, single-line, 200/200/600 chars) into the message the PA receives when the owner presses Add. The card shows all three (`apps/web/src/components/inbox-cards.tsx:191` renders `context`), so the owner sees what the PA will read; a pending suggestion never expires (worker's known gap). Fine as built.

## C. Nits
1. `google/connect.ts:65-77`: `--port` and `--timeout-minutes` are validated *after* the client file is read, so `pnpm connect:google --port 80` with no client file reports the missing client, not the bad port (observed). Validate flags first.
2. `google/accounts.ts:175-193` vs `226-229`: `remove()` clears the cache, but a `refresh()` already in flight can still `cache.set` for the removed account afterwards. Harmless today (sync tasks check `status = connected` first, `store.isCurrent`) but a stale in-memory token outlives the disconnect by up to ~1 h. Read, not run.
3. `GET /api/settings/google` runs `refresh()` (`inbox/accounts.ts:183-185`), so a GET can create timers (worker's known gap; idempotent).
4. `GOOGLE_HOSTS` (`google/oauth.ts:31-37`) allows any path on `www.googleapis.com`, so the host guard cannot tell a Calendar GET from a Gmail send; what actually enforces rule 1 is the GET-only client (`google/http.ts:71-75`) plus the read-only scopes. Fine; do not read the allow-list as a method guard.
